# AGPL・govtech 由来の重みを使わないモデル（実験版・デモには未採用）

デモ（`docs/models/`）のモデルは、検出器が Ultralytics の `yolov8n.pt` から転移学習したもの（AGPL-3.0）、
認識器が lpr_cpp（govtech パイプライン）の重みから学習したもの。ここにあるのは、そのどちらも使わずに
**ランダム初期化から**学習したもの。学習は 2026-11-08、Kaggle の T4。

| ファイル | 何か | どう作ったか |
|---|---|---|
| `plate_det_scratch_640.onnx` / `_320.onnx` | 検出器（yolov8n 構造、nc=1） | `train/plate_det_torch.py`（自前の PyTorch 実装）で 100 epoch。グラフは `jlpr init-det` が書き、重みを `train/export_onnx.py` で入れた（同じ重みを 640 と 320 の入力で） |
| `plate_ocr_scratch.onnx` | 認識器（11 head） | `jlpr init-ocr` のランダム初期化から `train/train_ocr_real.py` で 12000 step（balanced チェックポイント = step 9000） |
| `det_train_log.csv` | 検出器の学習ログ | epoch, box/cls/dfl loss, 合成 val の AP50, recall@0.25, 秒 |

学習データ: `jlpr gen` / `gen-det` の合成（GenSenRounded のみ）と dyama/alpr_jp（MIT）の実写プレート 720 枚。
実写プレートの分類番号・ひらがな・4 桁は `train/alpr_labels.tsv`（目視で書き起こしたもの）。
PlateYOLO-JP（AGPL）が付けた疑似ラベルは使っていない。

## まだデモに入れていない理由（次にやること）

1. **認識器が「ナンバーでないもの」にも高い確度を出す。** 看板や車体の一部を読んで 4 桁の確度 0.6-0.9 を返すので、
   解析器の「4 桁の確度 0.55 以上」というふるいを通ってしまう。現行の認識器は実データの地名以外を学習していないので、
   ナンバーでないものには低い確度を返していた。→ 背景の切り抜きと検出器の誤検出を「legible = 0」として学習に混ぜ、
   解析器のふるいに legible head を使う。
2. **検出器が実写の車ごとの場面に弱い。** 合成の評価セットでは現行と同等だが、テスト動画では白い車のナンバーを
   conf 0.05 でも拾えない（現行は 0.72）。現行は COCO で事前学習した重みから始めているので、実写の場面に慣れている。
   → alpr_jp の `train/sample`（固定カメラの車の写真 1309 枚、1920x1080、テスト動画に近い）に、このモデルで
   箱の候補を出し、目視で確かめて直した箱で微調整する。

## 見つけた不具合（yolo_lpr_cpp 側）

`fonts/DroidSansFallbackFull.ttf` には ASCII の数字が無い（CJK の補助フォントで、ラテン文字は別のフォントが持つ前提）。
`spec/fonts.txt` に入っているので、`jlpr gen` / `gen-det` の合成のおよそ半分で、4 桁と分類番号が豆腐（□）で描かれる。
ここの学習では DroidSansFallbackFull を外して GenSenRounded だけで生成した（検出器の合成データは直す前に作ったので、
描いたプレートの約半分は豆腐のまま。検出器は形しか見ないので影響は小さいと判断した）。
